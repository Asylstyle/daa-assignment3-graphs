## С чего начать
Проект использует Java 17 и Maven. Все алгоритмы работают с одним `graph.Graph`: список смежности, вершины от 0 до n-1, вес ребра int. Суммы весов, расстояния и счётчики имеют тип long. В неориентированном графе одно входное ребро даёт две записи смежности.

```sh
mvn clean test
java -cp target/classes graph.Main data/forest.txt
java -cp target/classes graph.Main data/dag.txt
java -cp target/classes graph.BonusMain data/critical.txt
```

В `algorithms` находятся реализации, в `metrics.Metrics` — счётчики, в `benchmark` — генераторы и измерения. В `src/test/java` лежат проверки по независимым эталонам. Основной результат — `results/results.csv`; отдельное сравнение SCC — `results/bonus-scc.csv`.

## DSU и минимальный остов
`DisjointSet` хранит parent[] и size[]. Корень множества указывает на себя. find сначала находит корень, затем сжимает путь; union присоединяет меньшее дерево к большему. Число компонентов уменьшается только после успешного объединения. С двумя эвристиками стоимость операции амортизированно O(alpha(V)), память структуры O(V).

`Kruskal` сортирует рёбра по весу. Инвариант: выбранные рёбра образуют лес, а DSU точно описывает его компоненты. Ребро добавляется только между разными компонентами. В связном графе можно остановиться после V-1 принятых рёбер. Время O(V + E log E), рабочая память O(V+E).

`Prim` начинает с вершины 0 и хранит рёбра границы в PriorityQueue. Уже посещённая конечная вершина означает устаревшее ребро: его пропускаем. Если очередь опустела, начинаем следующую компоненту. Для этой lazy-реализации время O(V + E log(E+1)), память O(V+E): очередь содержит рёбра, а не только V вершин.

**Почему оба верны?** Минимальное ребро, пересекающее подходящий разрез, можно включить в некоторый минимальный остов. Это cut property. При несвязном входе оба возвращают минимальный остовный лес и число компонентов.

## SCC: Kosaraju и Tarjan
SCC — максимальная группа вершин, каждая из которых достижима из любой другой.

`Kosaraju`: первый DFS записывает порядок завершения; затем строится транспонированный граф; второй обход в обратном порядке завершения выделяет компоненты. Оба обхода используют собственные стеки. Время O(V+E), дополнительная память O(V+E) из-за транспонирования. Счётчик DFS-просмотров равен 2E.

`Tarjan`: один DFS, два явных стека. Стек dfs хранит кадры незавершённых вызовов; active хранит вершины ещё не выделенных SCC. index[v] — номер открытия. lowlink[v] — минимальный индекс активного предка, достижимого через обработанные DFS-пути. После возврата ребёнка обновляем lowlink родителя; для ребра в уже открытую активную вершину используем её index. Ребро в завершённую SCC игнорируем. Когда lowlink[v] == index[v], снимаем active до v: это одна SCC. Время O(V+E), память O(V), просмотров E.

**Почему не сравнивать массивы номеров SCC напрямую?** Номера могут отличаться. Нужно сравнивать принадлежность пар одной компоненте или проверить взаимно однозначное соответствие номеров.

**Почему 100000 вершин не переполняют стек JVM?** Production DFS не использует рекурсивные вызовы. Максимальная глубина явных кадров учитывается в max_depth.

## Топологический порядок и короткие пути
`Kahn` помещает все вершины с нулевой входящей степенью в очередь. После удаления вершины уменьшает степени её соседей. Если обработано меньше V вершин, существует цикл. Проверка порядка отдельно требует position[u] < position[v] для каждого ребра.

`DagShortestPath` задаёт расстояние 0 всем источникам (indegree=0), затем расслабляет рёбра в топологическом порядке. Остальные расстояния сначала INF. Инвариант: при обработке вершины все её предшественники уже обработаны, поэтому её расстояние окончательно. Сохраняется parent[] для печати пути. Время O(V+E), память O(V).

**Почему допустимы отрицательные веса?** В DAG нет циклов, которые позволяли бы бесконечно улучшать путь. В общем графе отрицательные рёбра не всегда ошибка: Bellman-Ford работает с ними и обнаруживает достижимые отрицательные циклы.

## Конденсация и critical path
`Condensation` заменяет каждую SCC одной вершиной. Внутренние рёбра удаляются; каждое внешнее ребро сохраняет исходный вес, в том числе параллельные рёбра. Если бы между компонентами был направленный цикл, эти компоненты были бы одной SCC, поэтому конденсация всегда DAG.

`CriticalPath` ищет максимальную сумму весов от любого источника до любого стока DAG. Только источники получают начальное расстояние 0; остальные получают UNREACHABLE. Расслабление использует max вместо min — эквивалент поиска кратчайшего пути после смены знака весов, без риска переполнения при отрицании Integer.MIN_VALUE. В конце выбирается лучший сток. parent[] восстанавливает путь. Время O(V+E), память O(V).

В модели веса рёбер — длительности переходов, SCC-блоки имеют нулевую длительность. Внутренние длительности SCC не суммируются. Результат — путь по компонентам, а не самый длинный простой путь исходного циклического графа. Само наличие SCC с несколькими вершинами или петлёй в графе зависимостей означает проблему планирования, а конденсация лишь показывает связи между такими блоками.

**Отрицательная цепочка -5, +2?** Ответ -3 от источника до стока, а не 2: нельзя заново начать во внутренней вершине. Отрицательные веса поддерживаются математически, но обычные длительности задач должны быть неотрицательны. Изолированная вершина является источником и стоком с длиной 0. Пустой граф даёт длину 0 и пустой путь.

**Зачем critical path в расписании?** При неотрицательных длительностях он задаёт нижнюю границу времени завершения цепочки зависимостей при неограниченном параллелизме. Для длительностей на вершинах можно разделить каждую задачу на вход/выход и поместить её длительность на соединяющее ребро. Эта программа ожидает длительности на рёбрах и сама такого преобразования не делает.

## Что показывать в тестах и измерениях
Тесты сравнивают DSU с простой моделью, MST — между двумя реализациями, SCC — с BFS-достижимостью, кратчайшие DAG-пути — с Bellman-Ford. Tarjan также проверяется на пути и цикле из 100000 вершин. Critical path сравнивается с полным перебором маленьких DAG, отдельно проверяются циклы, отрицательные веса, параллельные рёбра и long-суммы.

```sh
java -Xmx4g -cp target/classes benchmark.Benchmark
java -Xmx4g -cp target/classes benchmark.BonusBenchmark
python scripts/analyze.py
python scripts/plot.py
```

Первый benchmark проверяет все значения преподавателя и пишет ровно 50 строк. Второй отдельно измеряет Kosaraju/Tarjan на десяти сочетаниях размера и плотности. Сравниваем прежде всего счётчики: часы зависят от JVM, прогрева и нагрузки. В отчёте явно указано, что подготовка входных степеней, транспонирование и топологическая сортировка исключены из отдельных scan-счётчиков, но включены во время.

**Почему график операций Kruskal не объясняется одним edge_scans?** Сортировка сравнивает все входные рёбра и даёт логарифмический множитель; счётчик просмотренных после сортировки рёбер его не включает.

**Что означает совпадение линий?** Некоторые алгоритмы считают одинаковое число выбранных операций. Это не означает, что их полный объём работы или время одинаковы.
